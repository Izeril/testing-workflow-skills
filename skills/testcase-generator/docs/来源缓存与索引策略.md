# 在线来源保存与敏捷索引策略

## 在线资料先保存，再分析

收到需求、提测或设计 URL 时，先检查需求目录的 .ai-internal/source_documents_manifest.json 及其中的本地正文。

- 本地正文可读：默认复用；报告列出页面版本和获取时间。本地修改标记 local_modified，不伪称网页最新版本。
- 缺少正文：通过可用连接器获取页面，转换成 UTF-8 Markdown，再调用主入口保存。
- 用户要求在线核对、刷新或提供明确更新版本：取得更新正文后显式刷新；旧版保存到内部历史。
- 已保存来源不可读或清单损坏：明确报错，不能悄悄联网或掩盖丢失。
- 用户排除旧资料：建立本次指定来源清单，分析仅用清单内正文，不读旧报告、脑图或其他需求作为事实。

正文必须放在需求文档/和提测文档/。直接引用的设计、接口正文放需求文档/，文件名带“设计方案”或“接口文档”。原始响应、来源清单、版本和内容摘要只放 .ai-internal/；只保存到输出缓存或临时目录不算完成。

获取和解析由 Codex 与连接器负责，保存脚本不含凭据、不访问网络。导入清单示例：

~~~json
{
  "documents": [
    {
      "kind": "requirement",
      "title": "需求标题",
      "url": "https://example.com/pages/viewpage.action?pageId=123",
      "page_id": "123",
      "page_version": 2,
      "page_updated_at": "2026-10-14T09:00:00+08:00",
      "markdown_path": "<本次获取并转换的 Markdown 路径>",
      "raw_json_path": "<本次原始页面响应 JSON 路径>"
    }
  ]
}
~~~

kind 支持 requirement/test/design/interface，亦兼容中文类型；正文也可直接通过 markdown 字段提供。

~~~powershell
python scripts/main.py "<需求目录>" --step check --source-documents "<来源清单 JSON>"
~~~

之后 --step analysis 默认读本地快照。明确刷新使用 --source-documents "<新清单>" --refresh-documents。普通导入优先复用同一 URL 已保存的正文，不要求临时下载文件仍存在。报告不能替代原始需求正文。

来源检查包括正文存在、可读且非空、标准目录位置、URL、内容摘要和版本记录。摘要变化作为本地修改披露，不覆盖用户编辑。评审链接清点必须使用同一缓存，将已下载正文识别为 linked_available。

## 固定提交，再判断索引风险

默认 repo.codegraph_policy: risk_based。保留索引版本检查，SHA 不同提示索引滞后，不能单独阻断需求分析或开发预分析。

1. 本次先固定开发、基线和 UAT SHA。变更范围、源码读取和合入核验均使用这些提交；后续新提交留到下次分析。
2. 索引用于候选入口、调用者、被调用者和数据依赖定位；旧索引关系保留在 navigation_*，不能作正式证据。
3. 索引与查询结果对齐目标时可接受图证据；否则回到冻结 SHA 补核关键入口、调用链、读写/配置行为及相关变更文件。
4. 正式 UAT 在关键影响覆盖仍不完整时阻断。合入、引用最新性、P0/P1 技术缺口、业务影响覆盖及人工决定仍是硬门禁。
5. 用户明确要求图索引与目标完全一致时用 --codegraph-policy strict；敏捷开发默认不用严格索引模式。
6. 无索引则跳过图工具，继续源码分析。维护仍需显式授权，不能自动 clone、创建工作树、复制索引、切分支或重建。mismatch 的停止要求仅限制未经授权的索引维护，不停止已授权源码分析。

通过 --impact-evidence "<JSON>" 或 repo.codegraph_impact_path 导入图结果与源码补核，多目标放 targets 数组。源码补核示例：

~~~json
{
  "targets": [
    {
      "target_id": "service",
      "source_verification": {
        "target_sha": "<冻结的完整提交 SHA>",
        "coverage_status": "complete",
        "unresolved_critical": [],
        "critical_paths": [
          {"path_id": "关键业务流程", "evidence_ids": ["SV-001", "SV-002", "SV-003"]}
        ],
        "evidence": [
          {"evidence_id": "SV-001", "file": "src/Job.java", "kind": "entry",
           "start_line": 10, "end_line": 12, "source": "<上述行的逐字源码>"},
          {"evidence_id": "SV-002", "file": "src/Service.java", "kind": "rule",
           "start_line": 20, "end_line": 25, "source": "<上述行的逐字源码>"},
          {"evidence_id": "SV-003", "file": "src/Job.java", "kind": "call",
           "start_line": 12, "source": "<实际调用行的逐字源码>",
           "caller": "Job.run", "callee": "Service.execute", "hop": 1}
        ]
      }
    }
  ]
}
~~~

关键路径必须覆盖入口和实际规则/SQL/配置；跨方法补 kind: call、caller、callee、hop。动态调用、路由或反射无法确定时列 unresolved_critical，不能填 complete。本次所有变更文件都需纳入已核验路径。代码目标清单可用 critical_impact_paths 列出必核业务路径 ID。

工作流逐条使用 git show <SHA>:<file> 核对源码与行号，并校验相对路径、SHA、最多 30 文件及最多两跳。空证明、错误 SHA、伪造原文或残缺路径不能放行。通过源码补核标 source_verified，不冒充索引已同步或图结果 ready。

按需或按提测批次维护索引，不要求每次提交重建。维护前仍做成本检查；预计超过 60 秒、200 MB 或复制完整仓库/索引的方案需明确授权。
