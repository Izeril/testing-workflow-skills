# 代码分析优化落地说明

## 运行模式

- `repo.analysis_mode: development`：显式启用开发分支预分析。允许使用本地缓存的 `origin/*`，但所有结论标记为预分析，不能宣称代码已经进入 UAT。
- `repo.analysis_mode: uat`：默认模式，执行正式 UAT 分析。默认设置 `refresh_remote_refs: true`，并在同一次定向 fetch 中刷新开发分支、基线和 `uat_branch`；仅离线预分析时使用 `--no-refresh-remote`。
- 默认 risk_based，索引差异提示；正式 UAT 要求有效图证据或冻结 SHA 的关键影响源码补核。strict 为显式严格图模式。

## 代码目标清单

多服务或共享开发分支建议使用 `--code-targets`：

```json
{
  "targets": [
    {
      "target_id": "java-tax-collect",
      "service": "tax-collect",
      "repo_path": "<repo-path>",
      "branch": "origin/feat_xxx",
      "baseline": "origin/master",
      "uat_branch": "origin/uat_merge",
      "analysis_mode": "uat",
      "requirement_id": "REQ-1234",
      "shared_branch": false,
      "commit_range": ""
    }
  ]
}
```

共享分支必须至少提供 `commit_range`、`pull_request`、稳定 `requirement_id` 或开发确认的 `changed_files`。需求关键词只参与文件和图结果排序，不会从已经确认的 Git 变更范围中删除文件。

## Codegraph 两步接入

1. 首次分析生成 `.ai-internal/codegraph_query_plan.json`。
2. Codex 使用 Codegraph MCP 按计划查询，将结果保存为配置项 `repo.codegraph_impact_path` 指向的 JSON 后重新运行分析。

结果格式支持：

```json
{
  "targets": [
    {
      "target_id": "java-tax-collect",
      "target_sha": "<uat_sha>",
      "relations": [
        {"caller": "ApplyController.submit", "callee": "ApplyService.submit", "hop": 1}
      ],
      "files": ["src/main/java/ApplyController.java"]
    }
  ]
}
```

最大跳数为 2，最大深度文件数为 30。动态代理、反射和运行时配置必须放入 `uncovered_dynamic_behavior`，不得伪装成确定调用关系。

## 新增产物

用户可见：

- `业务影响分析.md`

内部证据：

- `code_analysis_admission.json`
- `git_snapshot.json`
- `code_change_scope.json`
- `uat_merge_gate.json`
- `codegraph_query_plan.json`
- `codegraph_impact.json`
- `business_impact.json`
- `business_impact_gate.json`

测试设计覆盖矩阵新增 `business_impact` 和 `requirement_code_comparison` 映射，链路为：

```text
RQ → BI → RC → TP
```

`confirmed/high` 业务影响必须至少被一个测试点覆盖。`potential/unknown` 只进入待确认范围。正式 UAT 模式下，合入或引用最新性未验证、关键影响没有图证据或目标 SHA 源码补核、关键技术覆盖缺口或证据不足事项未决策都会阻断最终 XMind；默认索引 SHA 不同只提示，strict 模式才要求图索引完全一致。

## 只读保证

所有 Git 调用使用参数列表和 `shell=False`。工作流只执行 `rev-parse`、`fetch`、`diff`、`rev-list`、`merge-base`、`cherry`、`show`、`patch-id` 等读取或定向刷新操作，不执行 `pull`、`merge`、`push`、远程分支创建/删除或业务代码修改。




## 统一审计器接入（2026-10-14）

主入口的源码分析与需求比较统一调用 `requirement-code-auditor/scripts/workflow_api.py`，跨包边界仍为 `cross_skill_adapter.py`。当前工作流只需 testcase-generator、doc-to-md、requirement-code-auditor、xmind-generator 四个包；旧 code-analyzer、req-code-comparator 已移到 `.codex/skills-archive/`，活动契约只登记四个包的八个公开入口；归档包仅用于功能等价回归参照，不再由主入口调用。审计器依赖缺失时主入口报告依赖失败，禁止回退到归档包。

审计器包承接原有 Java/MyBatis、Python、SQL/存储过程、配置、调用链、接口输出字段及同分支依赖追踪，比较保留一致、缺失、不一致、额外实现、证据不足五类及部分覆盖策略。主入口继续使用原有需求事实、UAT 合入门禁、Codegraph/SHA 核验、业务影响、评审决策、覆盖矩阵与 XMind 产物链。

独立目录审计的 GitNexus 默认模式继续由 audit_runner 所有。主工作流组件使用明确传入的本地仓库/分支/SHA，不重跑目录审计、不读取其他批次报告，也不因远程失败自动回退。无代码目标仍跳过代码环节；指定目标分析失败仍阻断代码测试设计。

验证包括审计器全量回归、主工作流全量回归、归档原包与新包的临时 Git 混合技术栈结果对比、只安装四个核心包的隔离加载与契约检查，以及审计器缺失时拒绝归档回退和拒绝将旧包重新登记为活动依赖。


当前来源保存、CLI 及源码补核格式见 [来源缓存与索引策略](来源缓存与索引策略.md)。旧导航关系不作正式证据；合入、引用最新性、技术覆盖、业务覆盖和评审决定仍为硬门禁。
