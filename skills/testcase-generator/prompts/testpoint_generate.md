# 测试点生成提示词

> 此提示词用于 AI 从需求文档、评审报告和技术方案推导测试点

---

## ⛔ 禁止 AI 擅自做决定

| 禁止项 | 说明 | 正确做法 |
|--------|------|---------|
| 禁止假设已读取 | 不假设前置步骤已完成 | 每个步骤重新读取 |
| 禁止简化 Todo | 清单必须完整（12项） | 按规范创建完整清单 |
| 禁止跳过华库 | 必须读取华库学习 | 针对性加强遗漏场景 |
| 禁止跳过去重 | 必须执行去重合并 | 记录到 dedup_results |
| 禁止使用开发自测用例 | 开发自测仅作参考 | 测试点100%来自AI分析 |

## 条件阶段与结果真实性

代码业务影响仅在取得实际变更文件分析证据后执行。没有代码目标时记录 skipped 及原因，不输出空的业务影响报告；代码目标已指定但执行失败时保留 blocked，不降级为无代码。无代码的需求测试设计使用 RQ → TP，代码覆盖检查明确跳过；文件存在、空列表和错误数为0不能作为分析完成的证据。

```

  - 语义重复 → 删除（如"征信超时" vs "凯旋征信超时重试"）
  - 场景覆盖 → 删除（已有测试点已覆盖）
  - 新边界场景 → 保留
  - 新异常场景 → 保留

记录到 JSON dedup_results 字段
```

## ⚠️ 评审版测试点编写规范（覆盖视角）⭐

**核心原则：评审版节点标题只表达测试覆盖意图，不展开执行用例细节。测试数据、执行提示和详细预期放入 XMind 笔记。**
### 先抽取公共验证变量，再组织测试点

当一个需求同时修改多个接口出参、数据库字段、状态字段或配置项时，必须先抽取“被验证的公共变量”，再按变量组织测试点，禁止把不同变量的功能、边界、异常和回归场景平铺混排。

分组顺序：

1. 单一变量测试点：归入该变量节点。
2. 同时影响两个或多个变量：归入“变量A + 变量B（共同影响）”节点。
3. 在变量节点下，再按功能、参数化、边界、异常、接口、回归、性能、稳定性等场景类型细分。
4. 一个测试点只保留一个主要归属，避免在多个分组重复出现。

示例：

```text
partners.totalShouldCapi（认缴累计金额）
├─ 功能场景
├─ 边界场景
└─ 异常场景

partners.totalRealCapi（实缴累计金额）
├─ 功能场景
└─ 异常场景

partners.totalShouldCapi + partners.totalRealCapi（共同影响）
├─ 数据一致性场景
├─ 接口场景
└─ 回归场景
```

评审版测试点用于让用户快速判断覆盖是否完整、验证目标是否准确，因此每条测试点标题应尽量包含：

| 要素 | 说明 | 示例 |
|------|------|------|
| 验证对象 | 接口、表、字段、状态、任务或业务逻辑 | 处罚数据查询逻辑 |
| 关键条件 | 仅保留识别需求规则所必需的状态或边界 | is_history混合记录 |
| 期望行为 | 用户评审时一眼能看懂的业务结果 | 仅返回当前有效记录 |

### 术语必须展开

测试点标题不得使用需要评审人二次翻译的简称：

| 禁止简称 | 必须改写为 |
|---------|-----------|
| 主表 | 具体表名和字段，例如 `company_partner.stock_capital` |
| 明细求和 | 具体明细表和求和字段，例如 `company_partner_pay.stock_capital求和` |
| 比例公式/公式 | 完整计算关系，例如 `company_partner.stock_proportion×company_base.capital` |
| 兜底 | 明确触发条件、实际取值来源和输出字段 |

接口字段优化类测试点优先采用：`来源表.字段 + 条件/计算关系 + 输出字段`。
标题可以适当变长，但不能省略测试人员判断结果所需的表、字段和计算关系。

### 正确写法

```text
- 历史股东明细不参与金额合计
- keyword为空时返回明确的参数错误
- 本次变更不影响股东其他响应字段
- company_partner.stock_capital为0时按stock_proportion×company_base.capital计算totalShouldCapi
- totalShouldCapi按company_partner_pay.stock_capital精确求和
```

对应测试数据和执行说明写入笔记：

```text
覆盖依据：RQ-001、TE-001
测试数据：同一股东同时存在当前有效明细和历史明细
执行提示：调用目标接口并读取totalShouldCapi
预期结果：仅汇总当前有效明细，历史明细不参与合计
```

### 禁止写法

```text
- 测试查询逻辑
- 验证正常
- 操作步骤：打开Postman...
- 前置条件：准备测试数据...
- 主表认缴为0时执行比例公式
- 多条认缴明细精确求和
```

评审版不要生成“前置条件/操作步骤/预期结果”子节点。可辅助评审和执行准备的信息写入测试点笔记；正式操作步骤仍在用户评审确认后，由可导入版生成阶段基于评审终稿、需求、技术方案和代码证据重新细化。
## 评审版 XMind 结构规范 ⭐

```text
2026  ← 根节点（年份）
└── 202605
    └── 20260512
        └── 项目名称（从输出目录提取，无外层【】）
            └── <公司> [star-red]
                ├── KYM
                │   ├── 项目名称：xxx
                │   ├── 核心变更：xxx
                │   ├── 涉及表/接口：xxx
                │   └── 影响业务：xxx
                ├── 功能测试
                │   ├── 企业查询逻辑（步骤1）
                │   │   ├── 正常场景
                │   │   │   ├── keyword为企业全名，精准匹配存在企业，正确返回company_id
                │   │   │   └── keyword为统一社会信用代码，精准匹配存在企业，正确返回company_id
                │   │   └── 边界场景
                │   │       ├── keyword为空字符串，验证返回码和错误信息
                │   │       └── use_flag为NULL时的过滤行为
                │   └── 处罚数据查询逻辑优化（核心变更步骤2-3）
                │       ├── 正常场景
                │       └── 边界场景
                ├── 待确认问题
                └── 📖 评审标记约定（请阅读）
```

### 层级说明

| 层级 | 内容 | 格式 |
|------|------|------|
| 根节点 | 年份 | 2026 |
| 二级 | 年月 | 202605 |
| 三级 | 年月日 | 20260512 |
| 四级 | 项目名称 | 从目录提取，**无外层【】** |
| 五级 | <公司> | 带 `[star-red]` 标记 |
| 六级 | KYM/功能测试/异常测试/边界测试/待确认问题/评审约定 | 固定或按需求生成 |
| 七级 | 模块或核心变更点 | 如“企业查询逻辑（步骤1）” |
| 八级 | 场景类型 | 正常场景/边界场景/异常场景 |
| 九级 | 测试点标题 | 一句话表达验证对象、条件和期望行为 |

### 评审版与可导入版边界

- 评审版：只保留测试覆盖意图，便于用户新增、修改、删除测试点。
- 可导入版：评审完成后再生成前置条件、至少 3 条操作步骤和对应预期结果。
- 不要在评审版测试点下挂“操作步骤/预期结果”节点，避免评审阶段过重，也避免后续解析误把步骤当测试点。
## 规则库推断规则 ⭐

读取 `xmind-generator/rules_config.json` 通用初始规则及本机 `rules_config.local.json`（如有）；通过规则加载器合并后推断测试点步骤：

### 19种内置规则模板

| 类型 | 规则名 | 匹配关键词 |
|------|--------|-----------|
| 通用 | startup | 能否正常启动、任务启动 |
| 通用 | logging | 日志正确、日志完整 |
| 通用 | data_integrity | 数据完整性、数据总量 |
| 通用 | field_mapping | 字段映射、字段对应 |
| 通用 | exception | 异常处理、错误处理 |
| 定时任务 | full_sync | 全量同步启动 |
| 定时任务 | incr_sync | 增量同步启动 |
| 接口 | api | 接口调用、接口返回 |
| 配置 | config | 配置正确、配置生效 |
| 性能 | performance | 执行时间、响应时间 |
| 恢复 | recovery | 断点续传、中断恢复 |

### 推断优先级

```
1. 精确规则匹配 → 规则库中的精确关键词
2. 模板规则 → 带变量替换的模板（如 {table}, {service}）
3. 通用推断 → 提取核心动作，生成通用步骤
```

### 变量提取规则

| 变量 | 提取规则 | 示例 |
|------|---------|------|
| {table} | 从标题提取表名 | "验证company_base表数据完整性" → company_base |
| {service} | 从标题提取服务名 | "验证SFTP连接中断" → SFTP |
| {action} | 从标题提取动作 | "验证全量同步任务能否正常启动" → 全量同步任务 |

## 调用脚本

```bash
# ⚠️ 执行顺序：必须先生成 详细测试点.md，再调用 review_xmind.py
# 1. 生成 Markdown 格式的测试点文档（层级结构：## 一、大类 → ### 1.1 子类 → - 1.1.1 测试点）
# 2. 调用 review_xmind.py 传入 .md 文件

python "{skills_path}/xmind-generator/review_xmind.py" "<详细测试点.md路径>" "<输出目录>"

# ⚠️ 错误示例：不要直接传入 JSON 文件
# python review_xmind.py "<测试点.json>"  ← 这将解析为 0 个测试点
```
